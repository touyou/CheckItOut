## 2026-11-01 性能改善ループ 0 周目: 計測の土台と基準値 / perf/tap-latency-bench

- **背景**: パッドをタップしてから音が鳴るまでを短くしたい。まず測れるようにする（Step 0）と、基準値（Step 1）まで
- **判断**:
  - 点数は「指が触れた時刻（`UITouch.timestamp`）→ 音が出る時刻（推定）」。音が出る時刻はシミュレータで取れないので、
    `play()` が返った時刻 + `outputLatency` + `ioBufferDuration` の推定にした
  - 触れた時刻は、ウィンドウに付けた「何も認識しないジェスチャ認識器」で取る。SwiftUI の `Button` は
    触れた瞬間のイベントを出さないため
  - シナリオは初回タップ・同じパッドの連打・2 つ同時押し（点数に入る）と、ずらして取り消し・App Intents の再生（整合性だけ）
  - 計測用のコードは DEBUG だけ、かつ `-perf-tap-bench` で起動したときだけ動く。Release に入っていないことは
    `scripts/perf/release_check.sh` でバイナリの文字列を見て確かめる
  - プローブ（`Checkitout/PerfBench/`）と UI テスト、analyze.py、expected.json は基準の側のものを使う（bench.sh が上書きする）
- **整合性チェックのレビュー**（別のエージェントに 1 回、bench-harness.md 7 節のプロンプトで）: 23 件の指摘。扱い:
  - 直した: フックの値を呼び出し側の申告に頼らない（`willPlay` / `didPlay` でプローブが自分で時刻を取り、player の状態を読む）。
    音量・速さ・パンの確認、0.1 秒後もまだ鳴っているかの確認、連打が鳴っている途中に届いたかの確認、
    `play` に入った時刻が触れた時刻より前なら不合格、App Intents の再生中のカテゴリを 2 回見る、
    ログへの追記をロックで守る、README を書く
  - bench.sh の関門にした: `.xcodeproj`（ビルド設定・スキーム・ファイルの所属）、`AudioSample` の音源、
    アプリ側のフックの行が基準と違えば計測しない（人が見て許すときだけ環境変数で通す）。シンボリックリンクがあれば計測しない
  - Release に計測用のコードが入らないことを `release_check.sh` で確かめる
  - 直せないので README の「わかっている穴」に書いた: 音が本当にスピーカーから出たかは見ていない。
    アプリが自分でログを書くので、候補のアプリがログを書き換えることは原理的に防げない（フックの行の関門と差分のレビューで補う）。
    `PlaySoundIntent.perform` そのもの（`@Dependency` の解決）は通せない。計測は Debug ビルド
    （再生はほぼシステムのフレームワークの中なので、Debug と Release の差は小さいと見ている）。点数は p50 だけ（p95 は補助の指標で見る）。
    起動直後に音量 0 で先に鳴らしておく、のような温めは正当な最適化にもなるので、採否のときに人が見る
- **わざと壊して確かめた**: 連打で頭出ししない・パッド 2 の音量を 0 にした候補 → 0 点（4 種類の失敗を検出）。
  アプリ側にフックの行を足す・音源を書き換えた候補 → 関門で止まった
- **結果**（基準 3 回）: 点数 8.476 / 8.623 / 8.552、中央値 **8.552（ぶれ ±0.9%）**。遅れ **116.9 ms** の内訳（中央値）:

  | 区間 | ms | 動かせるか |
  |---|---|---|
  | 指を離すまで（`hold_ms`） | 83.0 | UI テストの押す長さ 0.08 秒。指を離したときに鳴る仕様だから入る |
  | 離してから `play` を呼ぶまで（`release_to_play_ms`） | 16.2 | うち 13.9 はシミュレータのイベント配送（`delivery_ms`）。SwiftUI の中は約 2 ms |
  | `play` の中（`play_call_ms`） | 12.4 | 初回 5.7、連打で鳴り直すとき 16.7 |
  | 音が出るまで（`output_est_ms`、推定） | 10.1 | セッションのバッファの長さ |

  シナリオごとの p50: 初回 113.5 ms、連打 124.5 ms、同時押し 110.0 ms
- **詰まった点 / 学び**:
  - XCUITest には、選んだ 2 点に同時に指を置く API が無い。`tap(withNumberOfTaps:numberOfTouches: 2)` は
    要素の中心の左右に、要素の幅の約 0.9 倍の間隔で指を置く。2 本指が 1 つのパッドに乗ると、SwiftUI の `Button` は鳴らない。
    パッドの境目に、ベンチのときだけ見えない要素を置いて、そこを叩いた
  - `PlaySoundIntent().perform()` をアプリから直接呼ぶと、`@Dependency` がランタイムの外でアサートして落ちる
  - UIKit は `UITouch` を使い回すので、ログの down と up を ID だけで結ぶと前の押下と混ざる
- **スキルの手順が合わなかった点**:
  - bench-harness.md は Web と GPU の描画を前提にしている。iOS アプリの UI 操作の遅れでは、
    「計測とチェックのコードを基準の側のものにする」がそのままでは効かない。プローブはアプリの中で動き、
    アプリのビルド設定（FileSystemSynchronized グループの所属の除外、ビルドフェーズのスクリプト）で外せるため。
    ファイルの上書きに加えて、`.xcodeproj` と音源の差分、アプリ側のフックの行を関門にする必要があった。スキルに戻す候補
  - 整合性チェックの「レスポンスのハッシュ」「画素の完全一致」に当たるものが音には無い（シミュレータでは出力を取れない）。
    player の状態（URL・再生中か・位置・音量）を見ることで代えた。自己申告にならないよう、プローブ側で読む形にした
  - 「Release に計測用のコードを残さない」の確かめ方がスキルに無い。バイナリの文字列を見るスクリプトを足した
- **確認**: `xcodebuild` の Release ビルド（generic iOS、署名なし）成功。`xcodebuild test`（ScreenshotTests 成功、
  ベンチのテストは `PERF_TAP_BENCH_OUT` が無いので skip）。ベンチ 3 回とも全チェック合格。`release_check.sh` OK。
  計測の土台なのでアプリの振る舞いは変えていない（Release で変わるのはパッドに `accessibilityIdentifier` が付くことだけ）

## 2026-11-01 性能改善ループ 1 周目: 設定「触れた瞬間に鳴らす」 / perf/play-on-touch-setting

- **背景**: 0 周目の内訳では、遅れ 116.9 ms のうち 83 ms が「指を離すまで」だった（離したときに鳴る仕様のため）。
  ユーザーが決めた仕様: 設定に「触れた瞬間に鳴らす」を足す。既定はオフで、いまと同じく指を離したときに鳴り、ずらすと取り消せる
  （「基本のユーザービリティとしてはキャンセルできる方が正しい」）
- **判断**:
  - 置き場所: アプリに設定画面が無く、設定はこの 1 つだけなので、モードの操作の並び（再生 / 編集・録音）の右端に
    歯車のメニューを足し、その中にトグルを置いた。トグルの下に「オフのときは指を離すと鳴り、ずらすと取り消せます」を添えた。
    アプリの文言は日本語の直書きだけ（文字列カタログはショートカット用だけ）なので、それに合わせた
  - 値は `@AppStorage("playOnTouchDown")`（`SettingsKey.playOnTouchDown`）
  - オンのとき、パッドは UIKit の認識器（`UIGestureRecognizerRepresentable`、`touchesBegan` で始まる）で鳴らす。
    押した見た目（押したときの画像と 0.95 倍の縮み）は、オフの `ButtonStyle` と同じ `PadFace` を使って揃えた。
    VoiceOver では `.isButton` の要素として読み、既定のアクション（ダブルタップ）で鳴る
  - 編集モードでパッドに音を割り当てる操作は、オンでも**離したとき**のまま（ずらして取り消せる方が、割り当てを間違えにくい）。
    オンで触れた瞬間に動くのは再生モードだけ
  - ベンチ: 期待値を設定ごとに分けた（ユーザーが決めた仕様の変更なので）。オフ: 離したあとに鳴る・ずらすと鳴らない。
    オン: 離す前に鳴る・ずらしても触れたときに 1 回鳴る。両方の設定で点数を出す。ベンチの変更はアプリの変更の前のコミットに分け、
    基準（main + ベンチ）と候補を同じベンチで測った
- **試して効かなかった案**: `DragGesture(minimumDistance: 0)` の `updating` で鳴らす → 触れてから約 85 ms、
  指を離す直前まで発火せず、整合性チェック（オンでは離す前に鳴る）に落ちた。UIKit の認識器に替えて通った
- **結果**（3 回の中央値、基準と交互に測った）:
  - オン: 点数 8.418 → **33.13**、遅れ 118.8 → **30.2 ms（-75%）**。触れてから `play` に入るまで 97.2 → 6.6 ms。
    シナリオ別の p50: 初回 114.3 → 23.5、連打 126.3 → 34.2、同時押し 109.5 → 28.8 ms。**採用**（点数で決めた）
  - オフ: 点数 8.418 → 8.705（+3.4%、ぶれ ±3.0% より大きい）。ただしオフの経路（`Button` → `play`）のコードは変えていない
    （見た目を `PadFace` にまとめただけ）。伸びの大半はシミュレータのイベント配送（`delivery_ms` 14.9 → 10.2、参考の指標）で、
    **成果としては書かない**。`compare.py` は `play_call_ms` の悪化（+6.0%）を出したが、`AudioEngine` は変えておらず、
    連打（`repeat_play_call_ms` -10%）と初回（-10%）はどちらも改善側なので、混ぜ方によるぶれと見た。オフは「悪化していない」で採用
  - 基準のオンは 0 点（設定が無いので離したときに鳴る）。オンは基準のオフと比べた
- **詰まった点 / 学び**:
  - SwiftUI の `DragGesture(minimumDistance: 0)` は、触れた瞬間の合図にならなかった。触れた瞬間を取りたいときは UIKit の認識器
  - ベンチの関門が、作業中のチェックアウトにあるビルド成果物（`.perf-runs/` の中の symlink）と、Xcode が作る
    `swiftpm/configuration` で止まった。調べる範囲を、コピーする対象と `project.pbxproj`・スキームに絞った
- **スキルの手順が合わなかった点**:
  - 「点数を 1 つにする」に対して、ユーザーが設定で 2 つの振る舞いを選べるようにしたので、点数が設定ごとに 2 つになった。
    「どちらも悪化させない」を採否の条件にし、compare.py を設定ごとに 2 回回した。スキルに「設定やモードで振る舞いが分かれるとき」の
    扱いがあるとよい
  - 仕様の変更でベンチの期待値を変える周は、「基準の側のコードで測る」とぶつかる（基準のベンチは新しい期待値を知らない）。
    ベンチの変更だけを先のコミットに分け、それを基準兼信頼できる側（`--trusted`）にして、基準と候補を同じベンチで測った。スキルに戻す候補
- **確認**: `xcodebuild` の Release ビルド（generic iOS、署名なし）成功。`xcodebuild test` 成功（ScreenshotTests、
  歯車が縦横どちらの画面にも収まることをスクリーンショットで確認）。ベンチ 3 回 × 2 設定で全チェック合格（オフ・オン）。
  `release_check.sh` OK。セキュリティだけのレビュー: 変更は UserDefaults の真偽値 1 つ・メニュー・タッチの認識器だけで、
  通信・データ・権限・課金に触れない。止める指摘なし。VoiceOver: オンのパッドが `.isButton` の要素として出ることは UI テストで
  確認した（`app.buttons["pad-N"]` で見つかる）。ダブルタップで鳴るかは実機で確かめてほしい
